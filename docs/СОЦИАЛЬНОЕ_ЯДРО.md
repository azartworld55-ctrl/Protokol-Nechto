# Независимое социальное ядро

Дата: 19 ноября 2026 года (Europe/Moscow)

## Область

Protocol.Social — независимый доменный модуль для отношений, личной памяти и передачи слухов. Он не ссылается на RimWorld, Verse, Unity, Harmony, Ports1de или проект генерации жителей. Идентификатор ResidentId содержит стабильный Guid, поэтому будущая интеграция с Protocol.Core.Resident.Id не требует хранения игровых объектов в домене.

Модуль не создаёт жителей, не определяет поле зрения, не обнаруживает разговоры и не знает скрытую роль паразита. Эти решения принадлежат вызывающему симуляционному слою.

## Отношения

- RelationshipLedger хранит направленное мнение наблюдателя о цели: A→B и B→A — разные записи.
- Доверие (Trust) и знакомство (Familiarity) — независимые целые шкалы 0–100.
- Изменения принимают long delta. Сначала выполняется сравнение с допустимым интервалом, затем сложение, поэтому даже long.MinValue и long.MaxValue не переполняют арифметику.
- Самоотношения запрещены. Неизвестная связь возвращает нулевые шкалы.
- Пороговые значения для передачи слухов задаются политикой, а не зашиты в модель отношений.

## Личная память

- У каждого жителя свой MemoryJournal, созданный для конкретного ResidentId.
- Прямая запись принимается только тогда, когда DirectObservation.ObserverId совпадает с владельцем журнала.
- Журнал не предоставляет глобального реестра памяти всех жителей.
- Entries возвращает отдельный read-only снимок. Приведение к IList<T> не позволяет изменить его, а последующие записи не меняют ранее выданный снимок.
- Идентификатор события дедуплицируется в пределах одного журнала.
- Владелец и содержимое записей неизменяемы. Доступ к чужому журналу возможен только если вызывающий код сам передал соответствующую ссылку; это граница возможностей API, а не криптографическая изоляция внутри процесса.

## Разговоры и слухи

- Передача требует явного ConversationEvent, в котором отправитель и получатель являются участниками. Близость, видимость или совместное нахождение на карте сами по себе не являются разговором.
- Вызывающий слой обязан создавать ConversationEvent только после подтверждённого события общения.
- Передаётся только событие, уже известное журналу отправителя. Получатель не может получить один event ID повторно.
- Порог доверия и знакомства, множитель затухания достоверности, минимальная достоверность и предел пересказов задаются RumorTransmissionPolicy.
- Достоверность хранится в тысячных долях: 1000 = 100%. При каждом пересказе применяется целочисленный множитель политики с округлением вниз.
- Первоначальный наблюдатель сохраняется, а последний информант, число пересказов и ID разговора обновляются.
- Слух не превращается в прямое наблюдение. Домен не раскрывает истинность события.

Тестовые значения политики (например, 750/1000) — синтетические fixtures, не утверждённый игровой баланс.

## Поток использования

1. Слой восприятия проверяет, что житель действительно наблюдал событие, и вызывает MemoryJournal.RecordObservation.
2. Слой симуляции создаёт ConversationEvent только после фактического общения двух жителей.
3. RumorTransmissionService.TryRetell получает два журнала, направленное отношение отправителя к получателю и явную политику.
4. Получатель получает отдельную запись HeardRumor; остальные жители ничего не узнают автоматически.

## Ограничения и следующий шаг

- Модель пока не соединена с Protocol.Core: генератор находится в отдельном Draft PR #4, не слитом в main.
- Не реализованы диалоги, расписания разговоров, вероятностный выбор тем, забывание, переоценка воспоминаний и сохранение через игровой save API.
- RelationshipLedger и MemoryJournal рассчитаны на последовательное обновление симуляцией; синхронизация потоков остаётся обязанностью вызывающего слоя.
- Никаких игровых API или предположений о Ports1de runtime в модуле нет.
