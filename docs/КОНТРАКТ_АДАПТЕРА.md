# Контракт игрового адаптера

Этот документ описывает границу между Protocol.Core и игровым адаптером. Он не предполагает конкретных имён методов Verse/Ports1de: точные API установленной сборки ещё не проверены.

## 1. Идентификаторы пешек

Адаптер должен назначать каждой игровой пешке устойчивый RuntimePawnId — строковый идентификатор, который не меняется при перемещении пешки, смене карты или перезагрузке сохранения. Нельзя использовать имя, отображаемый индекс в списке или текущую позицию.

ResidentRuntimeRegistry связывает этот идентификатор с Resident.Id:
- одна игровая пешка соответствует не более чем одному жителю ядра;
- один житель ядра соответствует не более чем одной игровой пешке;
- повторная регистрация той же пары допустима;
- конфликтующая пара отклоняется;
- при выгрузке/удалении пешки адаптер может убрать активную связь, но должен сохранить данные отдельно, если сущность может появиться снова.

## 2. Сохранение и восстановление

CreateSnapshot() создаёт ResidentRuntimeRegistrySnapshot с версией схемы и отсортированными связями. Адаптер должен сохранить этот DTO через собственный механизм сохранения игры и восстановить его при загрузке.

Снимок — контракт данных, а не готовая интеграция с RimWorld Scribe. В текущем коде ещё нет ExposeData, GameComponent или вызовов сохранения из игрового адаптера. При неизвестной версии схемы восстановление намеренно завершается ошибкой: нельзя молча назначать пешкам новые личности и портить сохранение.

## 3. Передача позиций и карты

Для одного логического шага симуляции адаптер собирает:
- ширину и высоту карты;
- ровно один MapCell на каждую клетку;
- для каждой активной пешки — её RuntimePawnId и координату GridPosition.

StationMapSnapshotBuilder преобразует runtime ID в Resident.Id и создаёт StationMapSnapshot. Неизвестный runtime ID, повторная запись одной пешки и недопустимые координаты не должны молча игнорироваться. Стены и закрытые двери передаются с BlocksVision = true; открытые двери — с BlocksVision = false.

Снимок должен отражать один согласованный момент игрового времени. Не смешивать позиции из разных тиков и не вызывать построитель на каждом кадре отрисовки.

## 4. Свидетели и личные знания

Построитель карты не определяет виновность, не рассылает события и не раскрывает расположение невидимых пешек. После расчёта обзора адаптер передаёт в социальные сервисы только фактически видевших событие жителей. Список свидетелей должен строиться по реальной позиции и линии видимости на момент события.

## 5. Что ещё не подключено

- чтение реальных клеток и позиций из Ports1de;
- получение устойчивого runtime ID от игрового объекта;
- сохранение/загрузка DTO через игровой save API;
- преобразование игровых событий в ResidentIncident;
- реальный Pawn/Map/Thing adapter и UI;
- сборка и запуск на конкретном устройстве.

Поэтому новые классы — протестированная граница ядра для будущего адаптера, а не заявление о готовой интеграции Ports1de.
