# Архитектура первого прототипа

## Срез состояния на 19 ноября 2026 года

Этот документ описывает целевую архитектуру и работу в нескольких открытых ветках, а не утверждает, что все перечисленные компоненты уже находятся в main.

- Protocol.ProfessionConfig и generic composer присутствуют в main.
- Protocol.Core с генератором 12 жителей находится в Draft PR #4 и ещё не слит.
- Новый независимый Protocol.Social с направленными отношениями, личной памятью и слухами находится в daily/2026-11-19; до слияния PR его нельзя считать частью main.
- PR #1 содержит более раннюю реализацию социальных систем, но остаётся открытым и расходится с main; его код не копировался в этот модуль.

## Почему код разделён на ядро и игровой адаптер

Целевая платформа проекта — Ports1de. Однако точные API и способ загрузки C#-сборок в установленной сборке Ports1de ещё не подтверждены.

Поэтому доменные модули не ссылаются на RimWorld, Waylith, Unity или Harmony. Когда будут подтверждены игровые сборки и API Ports1de, появится отдельный адаптер, связывающий ядро с объектами RimWorld.

## Уже реализовано в отдельных модулях/ветках

- Модель жителя с проверкой входных данных.
- Личностные параметры: любопытство, общительность, осторожность, эмпатия и дисциплина.
- Набор повседневных привычек, не отменяющих реакцию NPC на срочные события.
- Детерминированная генерация стартовой группы из 12 жителей по seed.
- Ровно один идентификатор паразита на группу.
- Игрок назначается только одному из 11 человеческих жителей.
- Проверка состава группы и запрет назначать игрока паразитом.
- Направленные социальные связи с независимыми шкалами доверия и знакомства (Protocol.Social, ежедневная ветка 19 ноября).
- Личный журнал наблюдений и услышанных слухов (Protocol.Social, ежедневная ветка 19 ноября).
- Передача слуха только после явного события общения, с затуханием достоверности при пересказе (Protocol.Social, ежедневная ветка 19 ноября).
- Состояние потребностей, расписание и автономные решения NPC — в незавершённой ветке PR #1; в main не интегрированы.
- Геометрия обзора, расчёт контактов, свидетелей и расследования — в незавершённой ветке PR #1; в main не интегрированы.
- Независимая конфигурация квот профессий и композиция 12 назначений в main.

## Социальный модуль Protocol.Social

- RelationshipLedger хранит направленное мнение наблюдателя о цели; A→B не приравнивается к B→A.
- Trust и Familiarity — отдельные шкалы 0–100. Изменения используют безопасную арифметику long и насыщение до сложения.
- MemoryJournal принадлежит одному ResidentId, принимает прямые наблюдения только от владельца и не предоставляет глобального доступа к журналам жителей.
- Entries возвращает read-only снимок, а не внутренний List.
- ConversationEvent — явный факт общения. Геометрическая близость и видимость не создают разговор.
- RumorTransmissionService передаёт только известное отправителю событие между участниками конкретного разговора.
- RumorTransmissionPolicy задаёт пороги отношений, множитель затухания, минимальную достоверность и предел пересказов; игровые значения не зашиты в код.
- Модуль не знает истинную роль паразита и не получает сведения о невидимых событиях.

## Пока не реализовано в актуальной линии

- Соединение Protocol.Social с Protocol.Core после интеграции PR #4.
- Диалоги, расписания разговоров, забывание и переоценка воспоминаний.
- Автономные потребности и рабочие циклы в актуальной линии main.
- Игровой адаптер Ports1de, сохранение через RimWorld save API и реальные Verse/Harmony hooks.
- Фактическая отрисовка mobile-first HUD поверх игры.

## Следующий шаг

После ревью социальных инвариантов интегрировать Protocol.Social с Protocol.Core и добавить сценарные тесты для 12 жителей. Не переносить API игры в доменные проекты до подтверждения runtime и DLL Ports1de.

## Конфигурация квот профессий

- Отдельный проект Protocol.ProfessionConfig читает версионированный JSON-документ с явно заданными квотами.
- Конфигурация отклоняется, если сумма не равна 12, ID пусты/повторяются или значения квот неположительны.
- ProfessionQuotaAllocator распределяет ровно 12 назначений с детерминированным Fisher–Yates и собственным SplitMix64 PRNG.
- ProfessionRosterComposer применяет этот список к уже сгенерированному упорядоченному ростеру из 12 элементов.
- Встроенного распределения профессий нет: список и количества должны поступить из решения по игровому балансу.
- Прямой вызов composer из StationRosterGenerator ожидает интеграции генератора из Draft PR #4.
- Код не использует RimWorld, Unity, Harmony или Ports1de API.
