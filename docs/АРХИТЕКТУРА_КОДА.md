# Архитектура первого прототипа

## Почему код разделён на ядро и игровой адаптер

Целевая платформа проекта — Ports1de. Однако точные API и способ загрузки C#-сборок в установленной сборке Ports1de ещё не подтверждены.

Поэтому первый код вынесен в независимую библиотеку `Protocol.Core`: она не ссылается на RimWorld, Waylith, Unity или Harmony. Это позволяет проверять базовые правила обычной сборкой .NET и тестами на GitHub Actions.

Добавлен отдельный проект Protocol.RimWorld, который связывает загрузку мода с Verse и Harmony. Его сборка требует DLL из конкретной установки; совместимость Ports1de ещё не подтверждена.

## Уже реализовано

- Модель жителя с проверкой входных данных.
- Личностные параметры: любопытство, общительность, осторожность, эмпатия и дисциплина.
- Набор повседневных привычек, не отменяющих реакцию NPC на срочные события.
- Детерминированная генерация стартовой группы из 12 жителей по seed.
- Ровно один идентификатор паразита на группу.
- Игрок назначается только одному из 11 человеческих жителей.
- Проверка состава группы и запрет назначать игрока паразитом.
- Социальные связи с независимыми шкалами доверия и знакомства.
- Личный журнал наблюдений и услышанных слухов.
- Передача слуха только после явного социального контакта, без глобальной рассылки.
- Вероятность передачи и достоверность слуха зависят от отношений.
- Защита от повторной передачи уже известного события одному жителю.
- Типизированные социальные события и правила их влияния на доверие и знакомство.
- Запись события в личные журналы участников и свидетелей; событие не становится автоматически известно всей станции.
- Реакции отношений применяются только для жителя, который действительно узнал о событии.
- Передача слуха может изменить отношение получателя к участнику события; слух остаётся помечен слухом и имеет сниженную достоверность.
- Состояние потребностей жителя: голод, усталость, потребность в общении и стресс.
- Выбор следующего действия на основе потребностей, времени суток, личности, привычек, отношений и личных воспоминаний.
- Часовой шаг симуляции, обновляющий потребности и назначающий автономные действия жителям.
- Рабочие смены с поддержкой перехода через полночь.
- Определение типа задачи по профессии (медицина, исследования, инженерия, кухня, обслуживание, связь).
- Планирование абстрактных рабочих поручений только для жителей на активной смене.
- Явная модель контакта двух жителей, поступающая от адаптера после проверки физической достижимости.
- Снимок карты на клеточной сетке с отдельными признаками блокировки движения и обзора; закрытые двери и стены перекрывают линию видимости.
- Геометрический обзор по радиусу с проверкой прямой видимости и защитой от просмотра по диагонали через угол стен.
- Отдельное вычисление видимых клеток и жителей для выбранного персонажа.
- Определение свидетелей события по их реальным позициям, радиусу и линии видимости.
- Поиск пар жителей, которые физически могут разговаривать; NPC вне обзора игрока продолжают иметь собственные контакты.
- Связка карты с социальным процессором: найденные пары автоматически передаются в систему контактов на выбранном социальном шаге.
- Персональная доска заданий человеческого игрока с приоритетами, статусами, завершением и HUD-снимком «МОИ ЗАДАНИЯ».
- Симуляция может быть привязана к конкретному player resident id; чужие персонажи не могут стать владельцем доски игрока.
- Обновление знакомства и передача одной известной участнику памяти как слуха только между участниками контакта.
- Учет рабочего расписания при выборе действия NPC: обычная работа не выбирается вне смены.
- Smoke tests для основных инвариантов.
- CI: проверка XML метаданных, сборка ядра и запуск smoke tests.

## Пока не реализовано

- Привязка рабочих поручений к реальным рабочим местам, помещениям и очереди задач на карте.
- Игровой адаптер Ports1de, который будет собирать реальные клетки карты, позиции пешек и передавать снимки в геометрический сервис.
- Передача вычисленных свидетелей в запись социальных событий игровым адаптером; геометрический сервис уже умеет возвращать список видевших событие жителей.
- Диалоги и генерация текстовых реплик.
- Долгосрочное забывание, вытеснение и переоценка воспоминаний.
- Многократное автономное распространение слухов между NPC по расписанию общения.
- Фактическая отрисовка HUD «МОИ ЗАДАНИЯ» поверх игрового экрана Ports1de и мобильная компоновка панели; ядро уже предоставляет готовый HUD-снимок.
- Поле зрения и интеграция с картой.
- Сохранение данных через механизм RimWorld.
- Игровой адаптер Ports1de.

## Следующий шаг

Геометрия карты и расчёт обзора реализованы в независимом ядре: стены и закрытые двери блокируют обзор, контакты NPC рассчитываются независимо от видимости игрока, а свидетели события определяются по позиции и линии видимости. Для игрока добавлена персональная доска заданий и готовый HUD-снимок «МОИ ЗАДАНИЯ». Следующий шаг — написать игровой адаптер Ports1de, который передаст в эти сервисы реальные клетки карты и позиции пешек, вызовет обработку свидетелей и выведет HUD-снимок на экран. Пока точные игровые API не подтверждены, фактическую интеграцию и отрисовку нельзя считать завершёнными.


## Расследования и обвинения

- `InvestigationCaseFile` хранит сведения по одному подозреваемому в рамках личного дела конкретного следователя. Чужие журналы памяти автоматически не читаются.
- `InvestigationEvidence` различает прямое наблюдение, физический след и слух. Вес слуха ниже; повтор одной и той же записи от того же источника не увеличивает оценку.
- `EvidenceAssessment` агрегирует силу сведений и число независимых источников, но не раскрывает истинную роль подозреваемого.
- `AccusationService` классифицирует обвинение как сильно обоснованное, правдоподобное, неопределённое или слабое и изменяет доверие между обвиняющим и обвиняемым.
- Это пока чистая модель ядра. Реальное обнаружение следов, регистрация свидетелей, UI расследования и арест через Ports1de не подключены.

## Задержание и побег

- `ResidentCustodyRegistry` хранит состояния Free, Detained, Released и Escaped для известных жителей.
- Каждый переход сохраняется в истории с игровым тиком и причиной задержания.
- Неудачная попытка побега оставляет жителя под стражей; успешная переводит его в Escaped.
- Ядро принимает исход попытки как входные данные. Камеры, охрана, физическое перемещение, вероятности и сенсорный UI должны быть реализованы игровым адаптером после изучения Ports1de API.


## Автономные решения паразита и реакция NPC

- `ParasiteObservation` принимает только кандидатов, которых игровой адаптер подтвердил как реально наблюдаемых паразитом. Отсутствие кандидатов означает отсутствие оснований для выбора цели.
- `ParasiteDecisionEngine` выбирает между наблюдением, ожиданием и преследованием уже замеченной возможности. Кандидаты с перекрытой линией обзора, присутствующими рядом жителями или чрезмерным риском подозрения не выбираются.
- `ParasiteMind` хранит только ранее замеченные идентификаторы и предпочтительную цель; он не получает глобальный список жителей и не читает скрытые позиции.
- `SuspicionResponseService` оценивает конкретного подозреваемого только по личному журналу одного NPC. Прямые наблюдения имеют больший вес, чем слухи.
- `SocialConsequenceService` может снизить доверие и предложить открыть расследование, но не устанавливает виновность и не вызывает автоматический арест.
- Социальная реакция не рассылается всем жителям: каждый NPC должен получить собственную память через наблюдение или явную передачу слуха.

Эти классы являются независимой моделью ядра. Адаптер Ports1de ещё должен передавать фактические наблюдения, позиции и видимость; до этого нельзя считать поведение подключённым к игровому миру.


## Инциденты и сборка доказательств

- `ResidentIncident` описывает событие станции, его участника, затронутого жителя, тип и тик.
- `IncidentMemoryService.RecordForObservers` записывает инцидент только жителям, явно переданным как свидетели адаптером. Событие не рассылается всем NPC.
- `TrySubmitKnownIncident` превращает личное наблюдение в прямое доказательство, а услышанное сообщение — в слух. Доказательство нельзя подать повторно из того же журнала.
- `TrySubmitPhysicalTrace` добавляет отдельно обнаруженный след; обнаружение следа и подтверждение его игровым событием остаётся обязанностью адаптера.

## Игровой адаптер RimWorld

В проекте появился отдельный Protocol.RimWorld для RimWorld 1.7 / .NET 10:

- Ссылается на локальные Assembly-CSharp и 0Harmony.dll.
- Не копирует игровые DLL или Harmony в сборку мода.
- Объявляет зависимость от brrainz.harmony.
- На старте логирует версии Verse assembly, Harmony и .NET.
- Пока не содержит игровых Harmony-патчей, преобразования Pawn в Resident, UI или управления камерой. Это намеренно: реальные сигнатуры и сборки Ports1de ещё не проверены.

Проект адаптера пока не входит в стандартный GitHub CI, потому что runner не имеет игровых DLL. Ядро продолжает собираться и тестироваться независимо.


## Устойчивые идентификаторы игровых пешек и снимки карты

- `ResidentRuntimeRegistry` связывает внешний runtime ID пешки с внутренним `Resident.Id` один-к-одному. Повтор той же пары безопасен; конфликтующая привязка отклоняется.
- `ResidentRuntimeRegistrySnapshot` содержит версию схемы и упорядоченный список связей. Это DTO для будущего сохранения, а не реализация RimWorld Scribe.
- `StationMapSnapshotBuilder` преобразует список runtime pawn ID и координат в `StationMapSnapshot`. Неизвестная пешка и дублирующееся наблюдение вызывают ошибку вместо молчаливой подмены личности.
- Адаптер обязан использовать стабильный идентификатор игровой сущности, сохранять снимок реестра вместе с сохранением партии и строить карту из согласованного набора данных одного логического тика.
- Реальные Verse/Ports1de API, источник стабильного ID, сериализация и фактическое чтение клеток пока не подключены и не проверены на устройстве.

## Мост игровых инцидентов

- `RuntimeIncidentBridge` связывает runtime pawn ID с Resident.Id и превращает игровой инцидент в запись личной памяти.
- Свидетели вычисляются через `StationPerceptionService.GetResidentsWhoCanSee` по снимку карты и координате события; стены и закрытые двери учитываются линией видимости.
- Затронутый участник получает личную запись как непосредственный участник; действующий и NPC вне обзора не получают её автоматически.
- Мост не создаёт доказательства и не объявляет виновность. Дальнейшая передача известных инцидентов в `IncidentMemoryService` остаётся отдельным действием NPC.
- Игровой адаптер пока должен передавать согласованный снимок карты и фактические журналы; Verse/Ports1de event hooks ещё не подключены.
