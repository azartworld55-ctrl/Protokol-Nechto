# Многоходовой обмен информацией в разговоре

Дата: 23 ноября 2026 года (Europe/Moscow)

## Назначение

ConversationExchangeService выполняет ограниченный обмен известными событиями в рамках уже подтверждённого разговора двух жителей. Это следующий слой над ConversationEvent и RumorTransmissionService: вместо одного вызова передачи вызывающий слой может передать упорядоченные повестки обоих участников и получить неизменяемую последовательность ходов.

Модуль передаёт структурированные сведения, а не генерирует естественно-языковые реплики.

## Контракт

Для одного обмена необходимы:

- существующий ConversationEvent с двумя разными участниками и временем;
- личный MemoryJournal каждого участника в том же порядке, что и ParticipantA / ParticipantB;
- общий RelationshipLedger;
- обязательная RumorTransmissionPolicy с порогами доверия/знакомства, затуханием достоверности и пределом пересказов;
- ConversationExchangePolicy с явным числом ходов;
- отдельная упорядоченная очередь EventId, которую каждый участник готов предложить как тему.

Очередь тем — только список предложений. Для каждой темы RumorTransmissionService.TryRetell заново проверяет, что отправитель действительно знает событие, получатель ещё не знает его, разговор не предшествует получению знания и отношения проходят заданные пороги.

## Порядок ходов

1. Первым говорит ParticipantA, затем участники чередуются.
2. За один ход предлагается не более одного EventId.
3. Успешная передача создаёт обычную запись HeardRumor с исходным наблюдателем, последним информантом, ID разговора, числом пересказов и сниженной достоверностью.
4. Отклонённая тема остаётся отклонённой; причина сохраняется в ConversationTurn.RejectionStatus.
5. Если очередь участника закончилась, в transcript записывается NoTopic. Отсутствие темы не создаёт память и не меняет отношения.
6. Результат содержит ровно заданное политикой число ходов и возвращается как read-only snapshot.

Предел политики — 1..32 хода. Каждая очередь может содержать не больше числа ходов, заданного для обмена; EventId должны быть непустыми и уникальными внутри очереди. Это техническое ограничение объёма одного вызова, не игровой баланс.

## Границы знания и ответственности

- Сервис получает только два переданных личных журнала; глобального хранилища знаний у него нет.
- EventId, которого нет в журнале отправителя, не может быть передан.
- Повторно известное получателю событие не дублируется.
- Сервис не создаёт ConversationEvent и не выводит факт общения из близости, видимости или общей локации.
- Физическую достижимость, расписание, начало и завершение разговора определяет вызывающий слой.
- Выбор тем также остаётся у вызывающего слоя; сервис сохраняет заданный порядок и не использует RNG.
- Домен не меняет отношения автоматически и не знает истинную роль паразита.

## Проверки

Отдельный проект tests/Protocol.Social.Conversation.Tests проверяет чередование, передачу в обе стороны, затухание и происхождение слухов, отсутствие утечки третьему жителю, отклонение неизвестных тем, временные и relational ограничения, неизменяемость transcript и воспроизводимость при одинаковых входах.

## Совместимость и лицензии

Код использует только существующий Protocol.Social и стандартную библиотеку .NET. Сторонние исходники, NuGet-пакеты, DLL, ассеты и игровые API не добавлялись. Лицензия репозитория не назначена. RimWorld, Verse, Unity, Harmony и Ports1de не являются зависимостями этого модуля.
