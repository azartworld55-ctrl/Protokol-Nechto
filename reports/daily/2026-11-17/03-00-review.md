## Что завершено

- Усилен `ProfessionRosterComposer`: он проверяет объявленный `Count`, затем перечисляет вход ровно один раз в ограниченный снимок. Снимок не может вырасти больше 12 элементов. Короткое или длинное перечисление отклоняется до вызова callback.
- Composer больше не использует `Enumerable.ToArray()` для пользовательской коллекции: LINQ может оптимизировать этот вызов через `ICollection<T>.CopyTo`, поэтому сломанная реализация `CopyTo` могла вернуть неполный массив, особенно опасный для value type.
- Все 12 входных элементов проверяются до назначения профессий. Callback вызывается ровно один раз на каждого жителя и только после успешной проверки полного входа.
- Снимок отделён от исходной коллекции: изменение исходного массива внутри callback не меняет уже подготовленный порядок жителей.
- Сохранены существующие гарантии: точные количества по конфигурации, стабильное распределение по seed, порядок жителей, read-only результат и запрет null-элементов/результатов callback.

## Найденная ошибка и исправление

**Ошибка на границе пользовательской коллекции.** Предыдущая реализация полагалась на `ToArray()`. Для реализации `IReadOnlyList<T>`, одновременно реализующей `ICollection<T>`, LINQ может использовать `Count` и `CopyTo` вместо перечислителя. Если такой пользовательский тип реализует `CopyTo` некорректно, массив может содержать default-значение вместо одного из жителей. Проверка null не защищает value type.

Исправление: composer копирует элементы через явный `foreach`, проверяет фактическое количество и прекращает перечисление на 13-м элементе. Добавлен регрессионный тест с намеренно некорректным `ICollection<T>.CopyTo` и value-type жителями; результат должен сохранить ID от 1 до 12.

Дополнительно добавлены проверки:
- `Count=12`, но перечислитель возвращает 11 элементов;
- `Count=12`, но перечислитель возвращает 13 элементов;
- перечислитель возвращает 12 элементов, но объявленный `Count` равен 11;
- callback не запускается для некорректной коллекции;
- callback запускается ровно 12 раз для корректного ростера;
- изменение исходного массива из callback не меняет снимок.

## Отдельный аудит социального ядра в PR №1

Социальное ядро находится не в ежедневной ветке, а в `feature/initial-social-core`. Я проверил исходники, не переносил эту ветку и не менял её: она расходится с актуальным `main` на 127 коммитов вперёд и 45 назад, GitHub сообщает `mergeable=false`. Все шесть review threads, связанные с проверенными инвариантами, остаются нерешёнными.

Результаты по обязательным правилам:

1. **Ровно 12 жителей — выполняется на уровне модели.** `StationRoster` проверяет размер, уникальность ID, принадлежность игрока и паразита ростеру и запрещает совпадение игрока с паразитом. Генератор создаёт 12 элементов.
2. **Воспроизводимость генерации — только в пределах текущего runtime.** `StationRosterGenerator` использует `System.Random(seed)`; тест сравнивает имена и назначения игрока/паразита, но не полный снимок всех полей 12 жителей. Между версиями runtime последовательность не является контрактом. Профессии пока выбираются случайно с возвращением, поэтому генератор не соблюдает точные квоты.
3. **Личная память — частично соблюдается, но граница доступа небезопасна.** Журналы хранятся отдельно, а сервис записи события получает явных наблюдателей. Однако `MemoryJournal.Entries` возвращает внутренний List под интерфейсом IReadOnlyList, а `StationSimulation.Minds` публично раскрывает все ResidentMind и их журналы. Это позволяет внешнему потребителю прочитать или изменить чужую память.
4. **Слухи только после явного общения — не соблюдается.** `SocialContactProcessor` принимает SocialContact, но `StationSocialContactRuntime.ProcessMapContacts` вызывает `DetectSocialContacts`, который превращает близость и линию видимости в контакт автоматически. Два молча стоящих рядом жителя могут повысить знакомство и передать память без события разговора.
5. **Симметрия и диапазоны отношений — частично соблюдаются.** Нормализация пары делает связь симметричной, а обычные изменения ограничиваются clamp. Но `current.Trust + delta` и `current.Familiarity + delta` вычисляются в Int32 до clamp. При `int.MinValue`/`int.MaxValue` возможно переполнение и нарушение диапазона.

Эти дефекты не исправлялись в PR №1 из ежедневной ветки: прямое изменение сильно разошедшейся ветки или перенос 66 файлов скрыло бы рискованный merge. На head PR №1 GitHub Actions runs и отдельные status checks не вернули результатов; CI для социального ядра здесь не считается пройденным.
